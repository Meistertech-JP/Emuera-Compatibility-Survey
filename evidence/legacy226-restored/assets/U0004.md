# FORCEKANA 0〜3と半角カナの出力比較

中断前のKANA0は `PRINTFORMLK` という未登録の命令名で読込エラーとなった。実際の変換を証明しないので保全し、別の正しい `PRINTFORMKL` を使った。

KANATEST0〜3は個別に `FORCEKANA 0`〜`3` を指定し、同一の混合文字列 `[あアｱ A]` と前後の目印を表示した。本家の各画面でBEFORE・対象文字列・AFTERに到達し、PyEmueraも各ケースで終了コード0となった。画像だけで文字のコードポイントは判定しない。

別のKANALOG01では、4設定を順に実行して同じ文字列を `PRINTFORMKL` で出力し、続けてOUTPUTLOGを実行した。新しい別ディレクトリで生成された両側のUTF-16ログから、各MODE行の直後のテキストを比較した。

| FORCEKANA | 本家ログ | PyEmueraログ | この文字列の結果 |
|---|---|---|---|
| 0 | `[あアｱ A]` | `[あアｱ A]` | 一致 |
| 1 | `[アアｱ A]` | `[アアｱ A]` | 一致 |
| 2 | `[ああｱ A]` | `[あああ A]` | **不一致** |
| 3 | `［あああ　Ａ］` | `［あああ　Ａ］` | 一致 |

設定2の半角カナについて、独立した最小ケースKANALOG02でも `FORCEKANA 2`、`PRINTKL ｱ`、`OUTPUTLOG` を実行した。本家ログは`ｱ`（U+FF71）、PyEmueraログは`あ`（U+3042）で、両者ともAFTERへ進んだ。これは入力動作の比較ではなくK付き表示とログの比較である。両ログが同じ意味の出力履歴を記録していることは、画面上の前後マーカー・OUTPUTLOG成功表示およびLOGFILE01_REVIEW_ja.mdの基礎比較で確認できる。EOF後のプロンプト・警告の一致は主張しない。

本家v24 ZIP同梱 `GameData/Expression/ExpressionMediator.cs:36–42,67–80` では2をHiragana、3をHiraganaとWideとして変換する。公開pyzの`pyemuera/printing.py:18–49`は2・3の両方で半角カナをNFKCで変換してからひらがな化する。該当コードは今回の観測の差を説明するが、すべての文字・OS設定での互換性を判定しない。半角記号、濁音、結合文字等は未検証。

入力ERB・本家exe・設定・PyEmuera pyzは各実行前後のSHA-256が一致し、KANALOG01・02のERBは両実行側でも一致する。出力ログのバイト・コードポイント、ログSHA、原票パスはFORCEKANA_KANA_LOG_COMPARISON.json。本家画面は `runs/native-fresh-KANALOG01-3315bada-display.bmp` と `runs/native-fresh-KANALOG02-5166d550-display.bmp`。本家原票はそれぞれ `runs/isolated-native-0e566c4aecfc42ef929615e03dbd0837/probe.json` と `runs/isolated-native-dd4852e9900d4ad997f8162fd53d728a/probe.json`。PyEmueraは `runs/kanalog-python-7c053302/`、`runs/kanalog02-python-304b7ec2/`。
